## Most likely remaining causes (ranked)

### 1. Product propagation timing (HIGH probability)

Google's billing service indexes products on a different cycle than Play Console UI. Products created via the Android Publisher API can take **24–48 hours** to become queryable from the BillingClient even when the UI shows them as ACTIVE.

Products were created today at ~10:00 UTC. Earliest reasonable retry: **2026-05-25 ~10:00 UTC**.

### 2. App signing key mismatch (MEDIUM probability)

If the APK's signing certificate doesn't match what's registered for the app's billing products in Play Console, billing silently returns empty results.

**To verify:**
- Play Console → **Setup → App integrity** → "App signing key certificate" SHA-1
- Compare to what Play Console expects under "Manage your in-app products and subscriptions"

Both should match.

### 3. Products need UI "Edit + Save" nudge (LOW probability)

User completed this for subscriptions but may not have for the lifetime in-app product. Untested.

## Update 2026-05-25 — Mongolia red herring + REAL root cause

### Mongolia theory: ruled out

`monetization.subscriptions.get` showed a Mongolian (MN) regional config on
all 3 products with `{currencyCode:"MNT", units:"10641"}` — missing the
`nanos` field. Suspected this caused Play Billing validation to silently
fail.

Wrote `scripts/play-console-strip-mn.mjs` to remove it. Script reported
"✓ patched" for all 3 products. **`scripts/play-console-inspect-regions.mjs`
confirmed MN was STILL there afterwards.**

Root cause of the silent-patch: `monetization.subscriptions.patch` with
`updateMask: 'basePlans'` is a NO-OP — base plans are NOT updatable via
the top-level subscription patch endpoint. The Play API returns 200 but
silently ignores the `basePlans` field. Same problem with
`monetization.onetimeproducts.batchUpdate` + `updateMask: 'purchaseOptions'`.

The `googleapis` JS library doesn't expose the actual basePlans/purchaseOptions
edit endpoints (only `.context` and `.offers`). Would need raw HTTP calls.
**But we didn't bother because MN turned out to be irrelevant** — see below.

### The actual bug: initConnection never completes

Pulled full analytics with `scripts/query-paywall-events.mjs`:
- `paywall_offerings_loaded` fires with `{count:0, raw_sub_skus:""}` on
  every device, every version (v1.8.0, v1.8.1, v1.8.2)
- `purchases_init_success` — **ZERO events ever**
- `purchases_init_failed` — **ZERO events ever**

`initPurchases` IS called from `app/_layout.tsx:163` (verified via grep).
Neither success nor failure branch fires → `m.initConnection()` either
hangs forever OR `loadIap()` returns null silently (the `if (!m) return`
path had no tracking event).

`fetchProducts()` is called from `getOfferings()` independently, with
`.catch(() => [])` — so it silently returns empty when billing isn't
connected. That's why we see mocks instead of real prices.

### Fix in v1.8.3 (`src/services/purchases/purchases.ts`)

- `initPromise` cached so `getOfferings()` awaits it (kills cold-launch race)
- 15s timeout on `initConnection()` → hangs surface as `purchases_init_timeout`
- Track events in EVERY branch:
  - `purchases_loadiap_failed` — require('expo-iap') threw
  - `purchases_init_skipped` — Expo Go or module unavailable
  - `purchases_init_module_shape` — confirms JS surface looks right
  - `purchases_init_connect_start` / `_done`
  - `purchases_init_timeout` / `_failed` / `_success`
  - `paywall_fetch_subs_threw` / `_onetime_threw` — actual fetchProducts errors
  - `paywall_fetch_without_init` / `paywall_init_await_failed`
